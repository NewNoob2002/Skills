# W09 重构规划

先用测试锁定现有行为，再分小步改动；每一步都能独立构建、测试和回滚。执行时按 [workflow.md](workflow.md) §3 的 checkpoint 推进。

## 概要

| 项 | 内容 |
| --- | --- |
| 触发 | 修复架构违规、拆分模块、C 迁移到 C++、调整分层 |
| 输入 | W02 的审查报告或违规清单；目标结构 |
| 前置条件 | 有行为基线：现有测试通过，或先补表征测试（characterization test）锁定当前的外部行为 |
| 角色 | Architect 制定计划；Developer 按步执行；QA 维护行为等价的证据 |
| 产物 | 分步计划（每步写明改动、风险、验证方法、回滚方式）、资源影响预估 |
| 人工审批 | 计划本身需要批准；执行时每个 checkpoint 默认请求继续许可 |

## 步骤

1. 建立行为基线：用表征测试覆盖将要改动的外部接口。
2. 对照目标结构列出差距，每项对应 Rule ID（例如 `ARCH-004`）。
3. 拆成小步：每步保持可构建、测试通过；先移动代码，再修改代码；接口变更单独作为一步。
4. 为每步定义验证：定向测试、`arch_lint`、`cpp_cost.py diff`。
5. 标出风险：改动涉及 ISR、时序或 DMA 路径的步骤需要 HIL 证据。
6. 回滚：每一步对应一个提交。

## 检查点

| 检查点 | 通过标准 | 不通过时 |
| --- | --- | --- |
| 行为基线 | 表征测试覆盖所有将要改动的外部接口 | 先补测试 |
| 步骤粒度 | 每步都能独立构建并通过测试 | 继续拆分 |
| 资源 | 每步的体积增量都在预算之内 | 重新设计该步 |
| 时序风险 | 涉及实时路径的步骤有 HIL 计划 | 补计划，或标 `NOT_RUN` |

## 通过与失败

- **PASS（计划）**：计划获得批准，且每步都有验证方法和回滚方式。
- **PASS（执行）**：每步完成后行为基线不变，`arch_lint` 的违规数不增加。
- **FAIL**：某一步改变了行为基线，此时回滚该步。
