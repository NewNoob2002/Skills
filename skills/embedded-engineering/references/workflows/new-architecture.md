# W01 新工程架构设计

深度固定为 Full（[workflow.md](workflow.md) §1），步骤细节见 [workflow.md](workflow.md) §2。

## 概要

| 项 | 内容 |
| --- | --- |
| 触发 | 新产品、新子系统、OS 或计算平台选型、跨核/跨处理器接口、资源预算或安全边界改变 |
| 输入 | 需求与验收标准（带编号）；候选芯片/板卡的精确型号与修订版；成本、功耗、实时、认证约束；可复用的现有资产 |
| 前置条件 | 需求可追溯；无法核实的硬件事实列为 `UNKNOWN`（`GEN-002`） |
| 角色 | Architect 主导并给出决策；QA 为每个模块定义所需的验证证据；Developer 只评估可实现性，不参与决策 |
| 产物 | 架构决策记录（上下文、拓扑、接口、评估矩阵、决策）；按依赖排序的模块清单；资源预算表；每个模块的验证计划；profile 判定 |
| 人工审批 | Phase 1 结束必须取得明确批准（`GEN-005`）；之后预算、安全边界或 OS 选型变化需要重新批准 |

## 步骤

1. 判定目标 profile：现有仓库运行 `scripts/detect_profile.py`；新工程对照 `profiles/*.yaml` 比较候选平台。
2. 收集上下文，每项标注事实 / 假设 / 实测，并写明来源。
3. 列出至少两个真正可行的拓扑（裸机、RTOS、Zephyr、Linux、异构）；只有一个可行时说明原因。
4. 接口优先：模块职责、输入输出、失败语义、时序期望、并发与所有权（MCU 见 [architecture/mcu-architecture.md](../architecture/mcu-architecture.md) §4）。
5. 资源预算：按 [cpp/features.md](../cpp/features.md) §2 确定资源等级 T0–T3，给出 Flash、RAM、栈、CPU 余量目标与测量方法。
6. 评估矩阵与决策（`Proceed / Revise / Reject`）。
7. QA 为每个模块写验证证据要求，后端按 [workflow.md](workflow.md) §5 的表选择。
8. 停在审批门，等待明确批准。

## 检查点

| 检查点 | 通过标准 | 不通过时 |
| --- | --- | --- |
| 上下文 | 每项有来源，或标 `UNKNOWN` 并说明影响 | 补齐，或列为阻塞项 |
| 备选方案 | 每个方案都满足硬性约束，或说明为何只有一个 | 结论改为 Revise |
| 接口 | 每个模块都有输入、输出、失败语义和时序 | 回到步骤 4 |
| 预算 | 每项都有目标值和测量方法；未测项标 `Unknown`，不编造数字 | 补齐 |
| 验证计划 | 每个模块至少一个证据级别，并由 QA 负责 | 补齐 |

## 通过与失败

- **PASS（可进入实现）**：决策为 Proceed、阻塞项为空，且用户已明确批准。
- **FAIL**：没有方案能满足硬性约束，结论为 Reject 并说明原因。
- **BLOCKED**：影响决策的关键事实仍为 `UNKNOWN`，例如外设能力尚未核实。
- 未经批准不得开始实现；沉默或泛泛的“去做吧”不算批准。
